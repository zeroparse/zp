# Generated Parsers

`zp gen` translates a grammar into the source of a standalone parser, in Go or
in TypeScript. A generated parser does not load or compile a grammar at run time
and does not depend on the ZeroParse engine. This chapter defines the generator, the
API of the generated Go and TypeScript code, the features each target supports
and where its behavior differs from the engine. Where this chapter does not state
a difference, a generated parser returns the same value, the same positions and
the same errors as the engine for the same grammar, input, start rule and
position unit.

## Scope and Terminology

The **engine** is the `zp.Parser` that parses with a compiled grammar. A
**generated parser** is the source that `gen.Go`, `gen.TypeScript` (package
`zeroparse.dev/zp/gen`) or `zp gen` writes. The **generation options** select optional parts of the
output. The **generated package** is the Go package named by `-pkg`; the
**generated module** is the TypeScript file. The generated Go code uses the runtime
package, which is the same for every grammar of one generator release, as a copy in
`internal/runtime` or imported from the module `zeroparse.dev/zp/runtime`; the TypeScript module includes its own runtime.
Every generated Go and TypeScript file starts with the line `// Code generated by zp <version>. DO NOT EDIT.`,
where `<version>` is the module version of the generator, or `(devel)` for a generator built without one.

## Contract

### The Generator

```text
zp gen -g <grammar> [-lang go|ts] [-module <import path>] [-pkg <package>]
         [-runtime embed|import|only] [-s <rule>] [-o <path>]
         [-types] [-document] [-stream] [-recognize] [-expectations] [-observability]
         [-source-info] [-default-value] [-nodoc] [-max-depth <n>]
         [-optimize <profile>] [-opt <name[=count],...>] [-no-opt <name,...>]
         [-print-after <pass,...>]
```

| Flag | Field of `gen.Go` / `gen.TypeScript` | Meaning |
|:--|:--|:--|
| `-lang` | `gen.Go` or `gen.TypeScript` | `go` (default) or `ts` |
| `-g` | the grammar argument of `Generate` | The grammar source: `.zp` or `.json`. A compiled grammar holds no grammar and is an error |
| `-module` | `Module` | Required for Go (with `-runtime import` only when `-pkg` is omitted); the import path of the generated package; rejected with `-lang ts` |
| `-pkg` | `PackageName` | The package name; MUST be a valid Go identifier; default: the last element of the import path without a major version suffix (`example.com/m/v2` gives `m`), and when that is not a valid identifier, generation fails and suggests `-pkg`; rejected with `-lang ts` and with `-runtime only` |
| `-runtime` | `Runtime` | How the parser reaches the runtime. `embed` (default) writes a copy of the runtime: `internal/runtime` in Go, `runtime.ts` in TypeScript. `import` imports it: `zeroparse.dev/zp/runtime` in Go, the module that `-runtime-module` names in TypeScript. A Go parser generated with `import` refers to the constant `ProtocolN` of the runtime protocol version N it was generated for, so it builds only against a runtime that implements that protocol. `only` writes just the copy (`GenerateRuntime`) and takes no grammar and no other generation flag |
| `-runtime-module` | `RuntimeModule` (`gen.TypeScript`) | TypeScript only, and required with `-runtime import`: the module specifier that `parser.ts` and `types.ts` import the runtime from, such as `../shared/runtime.ts`. Rejected with `-lang go` and with any other `-runtime` |
| `-s` | the start rule argument of `Generate` | The start rule, a rule marked `@start`. Default: the default start rule |
| `-o` | | For Go, the output directory (required), which the command creates; it writes `parser.go`, `api.go`, with `-types` `types/types.go`, and, with `embed`, `internal/runtime/*.go`, and removes generated files of an earlier generation that it did not write again (`only` writes and removes only files of `internal/runtime`, so it never removes `parser.go`, `api.go` or `types/types.go`). A file that lacks the `// Code generated by zp <version>. DO NOT EDIT.` header is never replaced or removed: the command fails before it writes anything. For TypeScript, the output directory (required): it writes `parser.ts`, with `-types` `types.ts`, and, with `embed` or `only`, `runtime.ts` |
| `-types` | `Types` | Generate typed values (see [Typed values](#typed-values)) |
| `-document` | `Document` | Generate the Go `Document` (Go only) |
| `-stream` | `Stream` | Generate `ParseStream` (Go only; the start rule MUST contain a `#stream` repetition) |
| `-recognize` | `Recognize` | Generate recognition without a tree |
| `-typed-only` | `TypedOnly` | Go only; needs `-types`. Generate only the typed entry points (`ParseAST`, `ParseRuleAST` and their options); there is no `Parse`, `ParseRule` or `Recognize`. Rejected with `-recognize`, `-document`, `-stream` and `-lang ts`. A typed entry point that converts the Node of its rule keeps the unexported Node rule functions it runs |
| `-expectations` | `Expectations` | Let a parse [record expectations](parsing.md#recording-expectations): what a syntax error expects and the messages of `@error`. The parser then has the table of expectations and a parse option `WithExpectations` (Go) or `expectations` (TypeScript); a parse records only when it passes the option, and otherwise a syntax error has the farthest position, an empty `Expected`, no `Messages` and the message `syntax error`. Without the flag the parser has no table and no option. A `Document` fixes the choice when it is created. It applies to every entry point, including the typed, `Document` and stream forms |
| `-observability` | `Observability` | Generate tracing and profiling, specified in [Observability](observability.md) |
| `-source-info` | `SourceInfo` | Make the parser record [source information](nodes.md#source-information): the rule of each node and the names of captures. Without it, `Node.Rule`, `Node.Field` and `Node.Fields` of a parsed node are empty and the outputs omit them |
| `-default-value` | `DefaultValue` | Make the parser return default values, as [Default Values](../language/actions.md#default-values) describes. Cannot be combined with `-types`, because the types come from the dropped actions |
| `-optimize` | `Optimize` | The [optimization profile](#optimization-options): `speed` (default, also the empty name), `memory` or `size`. An unknown profile is an error that lists the valid names. Rejected with `-runtime only` |
| `-opt` | `Opt` (a map from name to value) | Gives single optimizations a value, as `name` or `name=count`. Rejected with `-runtime only` |
| `-no-opt` | `NoOpt` | Turns the named optimizations off. Rejected with `-runtime only` |
| `-print-after` | `PrintAfter` and `PrintTo` | Writes the Core IR to standard error (`PrintTo`, which `PrintAfter` requires) after the named passes. Rejected with `-runtime only` |
| `-nodoc` | `OmitPackageDoc` | Omit the package comment (Go only; rejected with `-lang ts`) |
| `-max-depth` | `MaxDepth` | The default nested recursive rule-call limit; zero selects 100,000, a positive value overrides it, a negative value fails generation. TypeScript also requires a safe integer |

- The output is deterministic: generating twice yields identical bytes for the same grammar, options and
  version of the generator. Omitted,
  zero and an explicit 100,000 depth default generate identical source.
- Go output is formatted as by `gofmt`. Generated Go with the default `embed` runtime depends only on the
  standard library, and generated TypeScript has no dependencies. Generated TypeScript uses
  only erasable syntax and needs ES2020; it is type-checked under strict
  settings.
- Grammar errors are reported with positions before any file is written, in the
  same form as in other commands. An unknown start rule, an invalid package name,
  a compiled grammar (`gen needs the grammar source`),
  `-stream` without a `#stream` repetition in the start rule and a grammar that
  contains `#missing` are errors.
- A Go package may contain only one generated parser, because every generated file
  defines the same names. `api.go` re-exports the runtime names the users of the
  parser need, as aliases of the runtime's types and wrappers of its functions.
- With `-types` the Go types of the typed values are declared in the package
  `<module>/types` (the file `types/types.go`), which the parser package imports; a
  module path is required. The types package imports only the runtime, and
  declares a constant `ZPSchema_<digest>` that the parser package refers to once
  (see below). The
  parser package refers to the types as `types.Name`, and the users of the
  parser import `<module>/types` for them. The grammar's types therefore share no
  namespace with `parser.go` and `api.go`: a grammar type may be named `Node`,
  `Parser`, `Walk`, `ParseOption` or like any other export of the runtime.

### Optimization Options

An optimization is a named setting of the generator that changes the code a parser is generated as, and the
memory and time it needs, but not what it returns. It is either on or off, or it has a count where
`0` is off. Each optimization has a kind: `pass` (a transformation of the generator's intermediate
representation), `lowering` (an option of the step that lowers it toward the printers), `printer` (a choice
of what the Go and TypeScript printers emit) or `runtime` (a control of the runtime structures that the
printers emit). `zp gen -h` lists every optimization with its kind, its default and whether it takes a
count.

- **No option changes what a parser returns.** For every accepted combination of `-optimize`, `-opt` and
  `-no-opt`, the generated parser accepts and rejects the same inputs and returns the same trees, typed
  values, syntax errors and recovered errors, and the same trace and profile events, as one generated with
  the defaults. Options change only the generated source, its size and the time and memory of a parse.
  `-print-after` writes a diagnostic to standard error and changes neither the files nor the parser.
- **Profiles.** A profile is a fixed set of values and has no behavior of its own. `speed` is the default
  and sets every optimization to its default value. `memory` allocates typed values one by one instead of in
  slabs (fewer bytes and less live heap, more allocations). `size` produces smaller generated Go source
  and binaries for a little parse time.
- **Order.** The settings are the profile's, then the values of `-opt` replace them, then `-no-opt` turns
  optimizations off. `-no-opt` therefore wins over `-opt` for the same name.
- **Values.** `-opt name` is `name=1`. An optimization without a count takes `0` or `1`; one with a count
  takes `0` or a positive number. A name that is not an optimization, a value that the optimization does not
  take, a count that is not a decimal number, an empty item and a name given twice in `-opt` are errors, and generation fails before it writes a file.
- **Languages.** The options apply to Go and TypeScript. An optimization that concerns only one language,
  such as the slabs of typed Go values, has no effect on the other, and naming it is not an error.
- **`-print-after`** takes `build` (the Core IR as built), the name of a pass, or `all`. A pass that does
  not apply to the parser prints nothing. An unknown name is an error that lists the valid ones.

### Generated Go API

```go
func Parse(input string, opts ...ParseOption) (*Node, error)
func ParseRule(name, input string, opts ...ParseOption) (*Node, error)

type ParseOption func(*parseOptions)
func WithUnit(unit PositionUnit) ParseOption
func WithLimits(limits Limits) ParseOption
func WithContext(ctx context.Context) ParseOption       // with limit controls

type PositionUnit int
const (
	CodePoints PositionUnit = iota // the default
	Bytes
)
```

- `Parse` parses the whole input with the start rule. `ParseRule` does the same with
  the named start rule, a rule marked `@start`; another rule is the error
  `rule <name> is not a start rule; parsing can begin only at a rule marked @start`,
  an unknown name the error `rule <name> is not defined`, the name of a hidden
  rule the error that the rule is hidden, and an empty name selects the
  default start rule of the grammar. Both require the rule to consume the whole input.
  Generated parsers contain entry code only for start rules.
- `Node`, `Fields`, `NodeField`, `SyntaxError` and `SyntaxErrors` are types of the
  generated package (aliases of the types of its runtime) with the members of their
  engine counterparts, defined in
  [Nodes and Values](nodes.md) and [Parsing](parsing.md#syntax-errors). They are
  different Go types from those of package `zp`; errors are tested with
  `errors.As` against the generated types. Node JSON is identical to the engine's.
- Options apply in order. A final `Limits.Depth` of `Unlimited` returns a configuration
  error before matching, actions or named-rule lookup, because generated code nests rule
  calls on the host stack; zero selects the generated default. A nil option panics when applied. A call with no options uses code
  points and the generated depth default.
- A generated parser is safe for concurrent use: each call has its own state.
- Errors in actions (such as division by zero) return plain errors as in the engine, and
  exceeding the nesting limit returns a `*LimitError` of kind `LimitDepth`. The depth limit
  counts nested entries of recursive rules ([Limits](parsing.md#limits)); a larger limit does
  not guarantee stack capacity. The default error is
  `nesting too deep: more than 100000 nested recursive rule calls`.
- Every generated Go parser exports `WithLimits`, `Limits`, `LimitKind`, `LimitError`,
  `ErrLimit`, `LimitCompute`, `LimitInput`, `LimitDepth`, `LimitMemory` and `Unlimited`, and one generated
  with limit controls (`-limits`, `LimitControls`) also exports `WithContext`. A parser
  generated without them holds no code that spends budget or reads a control: one
  form of each function; with `-document` it is the form that serves a Document, without
  charges. A parser generated with limit controls has the controlled form only, and a parse that
  sets no limit runs it with the [default budget](parsing.md#default-limits). A parser generated
  without them, given a context or a finite `Compute` or `Memory` limit, returns an error
  that the parser was generated without limit controls; no option is ignored. A nil context,
  `Compute` and `Memory` limits that are zero or `Unlimited`, any `Input` and any `Depth` set
  no control and are accepted.
- `WithContext` and `WithLimits` apply the semantics of
  [Cancellation and Compute Limits](parsing.md#cancellation-and-compute-limits) to each
  invocation, with counters that restart for every call. They apply to named rules,
  recognition, typed parsing and conversion. The last context wins and `WithLimits`
  merges [field by field](parsing.md#default-limits); a nil context means no cancellation; a zero limit selects the
  [default](parsing.md#default-limits) and `Unlimited` disables it.
  An exhausted limit matches `ErrLimit`, and `errors.As` retrieves a
  `*LimitError` with `Kind` (`LimitCompute`, `LimitInput` or `LimitMemory`), `Limit`, `Used`
  and `Requested`. A finite `Memory` bounds the storage of the parse as the
  [memory limit](parsing.md#memory-limit) defines; the typed values of `-types` count too. An input longer than `Input` fails with `LimitInput` before any
  matching, in every entry point, and a generated stream fails when the parser reaches a
  unit beyond it. An interrupted entry point returns its zero result, and
  recovery does not turn an interruption into a successful partial tree.
  Cancellation is cooperative.

### Typed Values

With `-types`, the Go package also defines a Go type for each type of the grammar
and the functions

```go
func ParseAST(input string, opts ...ParseOption) (T, error) // T: the Go type of the start rule's type
func ParseRuleAST(name, input string, opts ...ParseOption) (any, error)
```

`ParseAST` returns the errors of `Parse`. The mapping of types is:

| Grammar type | Go type |
|:--|:--|
| `int`, `string`, `bool` | The same |
| Struct type `T` | `*T` with the same fields and an embedded `Span{Start, End int}` |
| `node[T]` | `*TNode[T']`, with `Span` and `Value` of the Go type `T'` of `T`: `*TNode[string]` for a string node, whose `Value` is the text, and `*TNode[any]` for `node[_]` |
| Tuple `(A, B, ...)` | `TupleN[A', B', ...]` with the fields `E0`, `E1`, ...; `Unit` for `()` |
| `error` (from `#recover`) | `*Error` with `Span`, `Text` and `Message` |
| Join `U ~ A \| B` of node types | An interface `U` implemented by `*A`, `*B` and `*Error` (and by every `*TNode[T]` if a member is a node type) |
| Join of declared node types written in place (a field, a list element, a rule value) and declared by no alias: `A \| B` (two or more distinct declared node types, with or without `error`), or `A \| error` (one declared node type and `error`) | An interface named after its members in the order of their first spelling in the file (declarations in source order, then the fields of a type), `AOrB`, or `AOrError` for one node type and `error`, implemented by `*A`, `*B` and `*Error`. The same set of members in any order is one interface, and a set that an alias declares is that alias. A type of the grammar with the generated name, or two different sets with the same name, is a generation error. A join with a member that is not a declared node type (`node[string]`, `node[_]`, a list, a scalar) has no interface and is `any` |
| `[]T` | A slice; an empty list is an empty slice and not `nil` |
| `*T` | `*int`, `*string` or `*bool` for basic types; otherwise the Go type of `T`, `nil` when absent |
| A rule whose type is not declared | The Go type of its value (an action's value maps by the rows above): `*TNode[TupleN[E0, ..., En]]` for a tuple of known elements, `*TNode[[]E]` for a list, `*TNode[Unit]` for the unit `()`; `*TNode[any]` when the elements are not known; a rule with a declared type, `node[_]` included, always has the Go type of that type |
| `_`, joins with basic members, with node members that are not declared node types, or with members of different shapes, a value that closes a cycle of rules | `any`, holding the converted value |
| Alias `Alias ~ T` | A Go alias to the value type of `T` |

- `TNode[T]` is `struct { Span; Value T }`; `TupleN` is `struct { E0 E0; ...; En En }`
  and `Unit` is `struct{}`. A missing element of a tuple is `nil`. A list node's `Value` is a slice.
- A grammar type keeps its name. The types package declares, besides the grammar's
  types, `TNode`, `Error`, `ZPHooks` and, when used, `Unit`, `TupleN` and
  `ZPNodeTypes`, and a constant `ZPSchema_<digest>`; generation fails, naming the
  type, if a grammar type has one of these names. The digest covers the package's
  declarations, not its comments or formatting. The parser package refers to the
  constant once, so a `parser.go` and a `types/types.go` generated from different
  schemas do not compile together; the runtime relies on this when it reads a string
  node as its named node type. A grammar type named `Unit` is an error only when the generated
  code uses the empty tuple, and one named `TupleN` only when it uses a tuple of
  that arity. A struct field named like a field or method of the embedded `Span`
  (`Start`, `End`, `Range`) or like a method of the typed values (`TName`, ...)
  gets a trailing underscore in Go (`Start_`), so `Start` and `End` always read
  the span; the value still reads back under the grammar name. Every declared alias is exported.
- After `#recover`, an error value in a list of a join type stays in the list as
  `*Error`; where a struct type is expected it becomes `nil`.
- `ParseRuleAST` consumes the whole input, applies options once before it looks up
  the name, and returns the selected start rule's typed value as `any`. Names that
  `ParseRule` rejects, with the same errors, and invalid options return `nil` with an
  error. A parse failure returns the zero value
  of the selected type. `ParseRule` continues to return `*Node`.
- A generator MAY build typed values directly instead of converting the tree
  that `Parse` returns when every value has a Go type of its own; the result is the
  same either way.

Typed TypeScript output (`-types`) exports an interface for every struct
and alias and the functions `parseAST` and `parseASTWithOptions`, which parse the
configured start rule and convert the node result. They return `{ value, error }`:
a successful nil result has a null value and a null error; a failure has a null
value and the error; recovery keeps the converted value and `SyntaxErrors`. The
mapping is:

| Grammar type | TypeScript value |
|:--|:--|
| Struct | An interface with `type` (the grammar name), `start`, `end` and the fields; nullable where an absent or incompatible recovered value becomes nil |
| `node[T]` | `TNode<T'>`, with `start`, `end` and `value` of the TypeScript type `T'` of `T`; `StringNode`, which extends `TNode<string>`, for a string node, and `TNode<unknown>` for `node[_]` |
| Tuple `(A, B, ...)` | `readonly [A', B', ...]` |
| `[]T` | A readonly array, or null; null differs from an empty array |
| `*T` | A nullable target |
| `int` | `number \| bigint`, with signed 64-bit arithmetic and safe-number canonicalization |
| `string`, `bool` | `string`, `boolean`; an absent non-optional scalar field is `""`, `false` or `0` |
| Declared alias | The complete target type |
| Join of declared node types, declared by an alias or written in place | The member interfaces, `RecoveredError` and null; tuple and list node members remain `Node` |
| Join with a member that is not a declared node type, `_` | `TypedValue`, following the conversion of `any` in Go |

Names collide the same way as in Go, with trailing underscores. Typed parsing by
rule name is not available in TypeScript.

### Recognition

With `-recognize`, Go gains `Recognize(input string, opts ...ParseOption) error` and
TypeScript gains `recognize` and `recognizeWithOptions`. They check that the whole
input matches the start rule without building a tree and return the errors that
`Parse` returns, including `SyntaxErrors` for recovered errors. Actions whose values
are not read by predicates are skipped; actions that predicates read still run and
can report runtime errors.

### Incremental Documents (Go Only)

With `-document`, the Go package gains `NewDocument(text string, opts ...ParseOption) (*Document, error)` and a
`Document` with these members: `Parse`, `Edit(start, end, replacement)`, `Text`,
`Stats` and, with `-types`, `ParseAST`.

- `Edit` replaces a half-open range in the position unit chosen at construction. It
  rejects an invalid range, and a position inside a UTF-8 character in `Bytes`
  mode, without changing the text. `Text()` returns the exact current input.
- Construction options become the defaults of later calls. A call MAY set the
  depth, the context and the compute limits; it MUST NOT change the unit.
- `ParseStats` has the fields `Evaluated` and `Reused`.
- A parse returns what a parse of the whole current text returns. An interruption
  discards memo history so that a later call can retry.
- A `Document` is for one goroutine. A returned tree can share nodes with later
  parses; `Node.Clone` makes a detached copy that preserves cycles and repeated
  references. With `-types`, `ParseAST` returns read-only values that share storage
  with the document and with earlier results. Caller mutation can therefore change
  what later results contain, as with `Node` values. `CloneAST(value)` returns an
  independent copy that shares nothing with the document or other results, and
  preserves aliases within the copy. Every slice in a returned value has capacity
  equal to its length, so `append` on a result cannot write into another result.
- The returned `SyntaxError` values and their `Expected` and `Messages` slices are
  owned by the caller. Parsing, diagnostic copying and typed publication share one
  budget.
- It supports a subset of the engine's [Incremental Documents](documents.md): there
  is no `EditBatch`, no `Version`, no snapshots and no change notifications.

### Streaming (Go Only)

With `-stream`, the Go package gains `ParseStream(r io.Reader, emit func(*Node) error, opts ...ParseOption) error`,
`Iterate` with `StreamIterator` and `ErrStreamClosed`, and the options
`WithDiagnosticCallback` and `WithDiagnosticLimit` with `TruncatedSyntaxErrors`. They
follow the contract of [Streaming](streaming.md), with these differences: a nil
`emit` parses the stream without delivering elements, and the diagnostic options are
accepted only by the stream entry points (`Parse`, `ParseRule`, `ParseAST`,
`Recognize`, `NewDocument` and `Document` methods reject them). `Parse` treats
`#stream` as an ordinary repetition.

With `-types` as well, the package gains `StreamValue`, `ParseStreamAST` and
`IterateAST` with `StreamASTIterator`. `StreamValue` is the Go type of one element
of the `#stream` repetition, not of the start rule. Each element is converted on
its own when it is committed, so the value stays valid after the callback returns.
The conversion counts toward the compute limits and observes the context.

### Generated TypeScript API

```ts
export function parse(input: string | Uint8Array, unit?: Unit): ParseResult;
export function parseRule(name: string, input: string | Uint8Array, unit?: Unit): ParseResult;
export function parseWithOptions(input: string | Uint8Array, options?: ParseOptions): ParseResult;
export function parseRuleWithOptions(name: string, input: string | Uint8Array, options?: ParseOptions): ParseResult;

export interface ParseOptions {
  unit?: Unit;
  signal?: CancellationSignal | null;      // with -limits only
  limits?: Limits;
}
export interface Limits {
  compute?: number;                       // with -limits only
  memory?: number;                        // with -limits only
  input?: number;                         // with -limits only
  depth?: number;
}
export const Unlimited: number;           // Number.MAX_SAFE_INTEGER
export interface ParseResult { node: Node | null; error: Error | null }
// With -limits:
export interface CancellationSignal { readonly aborted: boolean; readonly reason?: unknown }
// In both forms:
export type ParseInterruptionKind = "canceled" | "compute-limit" | "memory-limit" | "input-limit" | "depth-limit";
export class ParseInterruptionError extends Error {
  readonly kind: ParseInterruptionKind;
  readonly limit: number;
  readonly used: number;
  readonly requested: number;
  readonly cause: unknown;
}
export type Unit = 0 | 1;
export const CodePoints: Unit; // the default
export const Bytes: Unit;
export function marshal(n: Node | null): string;
```

- **Public names.** The public API of a generated TypeScript parser is what `parser.ts` exports, plus the names of
  `types.ts` with `-types`. From the runtime it re-exports `Value`, `Unit`, `CodePoints`, `Bytes`, `NodeField`,
  `NodeJSON`, `Node`, `marshal`, `SyntaxError`, `SyntaxErrors`, `ParseResult`, `ParseOptions`, `Limits`,
  `ParseInterruptionKind`, `ParseInterruptionError`, `Unlimited`, `TraceKind`, `TraceEvent`, `Profile`,
  `ProfileLocation`, `SkipReasonCount`, `RuleProfile` and `ProfileSnapshot`, and with `-limits` also
  `CancellationSignal`. Without `-limits` the exported `ParseOptions` and `Limits` are the forms without `signal` and
  `limits.compute`. `TraceKind` is `"enter"`, `"exit"` or `"skipped"`. The other exports of `runtime.ts`, such as
  `ProfileData`, are the contract between the runtime and the generated code. They are not
  public API and may change between versions.
- `parse` does not throw for bad input: it returns `{ node, error }` with a node and
  no error; no node and an error; or, after `#recover`, a node and `SyntaxErrors`.
  It throws only for defects that are not parse errors.
- `Node` has `type`, `rule`, `start`, `end`, `text`, `children`, `fields`, `field(name)`,
  `isTerminal()`, `toString()` and `toJSON()`, with the meaning given in
  [Nodes and Values](nodes.md). A field value is a `Node`, a number, a bigint, a
  string, a boolean or `null`.
- `SyntaxError` has `pos`, `line`, `col`, `expected`, `messages` and `reason()`, and
  its `message` is the text of the engine's error; `SyntaxErrors` has `errors`.
- The `SyntaxError` values of `SyntaxErrors`, the errors that `#recover` recovered from, carry
  only the header line in `stack`; the `error` of a parse that failed keeps the stack of the
  point where it was made.
- `marshal(node)` returns exactly the bytes that `encoding/json` writes for the
  engine's node. `JSON.stringify` yields the same keys in the same order, except
  that integers beyond the safe range are rounded and, in `Bytes` mode, an invalid
  input byte is written as the surrogate that represents it.
- `marshal` and `toString` write trees of any depth. `JSON.stringify` recurses and
  can exhaust the stack for deep trees.
- `limits.depth` MUST be a positive safe integer or zero; `Unlimited`, negative values,
  fractions, NaN, infinity and unsafe integers return a configuration error in the result
  before matching, because rule calls nest on the JavaScript stack. Omitted or zero selects
  the generated default. A parse that nests more recursive rule calls returns `node` as
  `null` and `error` as a `ParseInterruptionError` whose `kind` is `"depth-limit"`, with
  `limit` and `used` the depth limit and `requested` 1, in both forms.
- A parser generated without `-limits` emits no code that spends budget and sets no control, so a parse charges nothing, and its
  `ParseOptions` has no `signal` and its `Limits` has no `compute` or `memory`; it does not
  export `CancellationSignal`. A call that passes a signal or a finite nonzero compute or
  memory limit anyway returns an error in the result, before
  matching, that says the parser was generated without limit controls; no option is
  ignored. An absent or null signal, zero or `Unlimited` compute and memory limits, and the input
  and depth limits set no control and are accepted. A parser generated with `-limits` has the controlled form only, and a call
  that sets no limit runs it with the [default budget](parsing.md#default-limits). The rest of this list describes the controlled form.
- `signal` is a structural cancellation signal: any object with `aborted` and an optional
  `reason`, such as an `AbortSignal`. `limits.compute`, `limits.memory` and `limits.input` MUST be finite
  nonnegative safe integers; zero selects the [default](parsing.md#default-limits) and
  `Unlimited` (`Number.MAX_SAFE_INTEGER`) disables the limit; other values return a
  configuration error in the result. An unknown option or limit key, such as `limits.time`,
  is a configuration error too, in both forms. A finite `limits.input` bounds the input in the
  position unit and is checked before any matching, in both forms; a longer input returns a `ParseInterruptionError` whose
  `kind` is `"input-limit"`, with `limit` the input limit, `used` zero and `requested` the length
  of the input. The units of the limits are those of
  [Cancellation and Compute Limits](parsing.md#cancellation-and-compute-limits).
- A finite `limits.memory` bounds the storage the parse takes into use, in bytes, as the
  [memory limit](parsing.md#memory-limit) defines it, with the polls, order of checks and
  accounting given there. The count is an estimate from a model of the sizes of the
  runtime's objects in a 64-bit JavaScript engine: the nodes, child lists and fields the
  parse builds, memo entries, slots and hash indexes, first-call sets, the decoded input
  and its line table, the records of left recursion and of scan and skip sites, variable
  environments and frames, syntax errors, the text copied out of the input and the strings
  that actions concatenate, and the slots of the working stacks at their largest length
  at a poll. Not counted are the caller's input, the values of the typed conversion that
  `parseAST` hands to the caller, and what the JavaScript engine adds beyond the model.
  A count above the limit returns a `ParseInterruptionError` whose `kind` is
  `"memory-limit"`, message `memory-limit exceeded: limit N, used M`, with `limit` the
  memory limit, `used` the count and `requested` zero.
- An interrupted parse returns `node` as `null` and `error` as a `ParseInterruptionError`
  whose `kind` is `"canceled"`, `"compute-limit"`, `"memory-limit"` or `"input-limit"`. For a limit,
  `limit`, `used` and `requested` give the accounting, with the meaning that
  [a `LimitError` reports](parsing.md#cancellation-and-compute-limits); for cancellation, `cause` is the
  `reason` of the signal. Recovery does not turn an interruption into a partial result,
  and the parser keeps no reference to the signal after the call returns. Typed
  conversion (`parseAST`) and recognition report interruptions the same way.
- A synchronous parse does not yield to the event loop: a signal that changes only
  through timers or other tasks of the same thread is not observed during the call. A
  signal that is already aborted is observed at the first poll, and the compute limits do not
  depend on the event loop.
- With `-recognize`, `recognize` and `recognizeWithOptions` return `null` if the
  input matches and an `Error` otherwise. With `-observability`, the batch entry
  points accept the tracing and profiling options of [Observability](observability.md).
- A generated TypeScript module exports the same names for every grammar, so two
  parsers are imported under different namespaces. A parser keeps no state between
  calls.

### Input and Positions in TypeScript

Positions count Unicode code points (the default) or UTF-8 bytes (`Bytes`), as in the
engine, and not UTF-16 code units. The parser decodes the input first.

- A string is parsed as its UTF-8 encoding would be. A lone surrogate becomes U+FFFD.
- A `Uint8Array` is parsed as UTF-8 bytes; an invalid sequence decodes to U+FFFD, one
  per byte, as in Go. In `Bytes` mode, positions count the original bytes.
- In `Bytes` mode, text keeps the bytes: each invalid byte *b* is represented by the
  lone surrogate U+DC00+*b* in node text and in `text(...)`. `marshal` writes such a
  byte as U+FFFD.
- String operations in actions follow Go: `+` concatenates, comparisons order by
  code point, and `len` counts code points or UTF-8 bytes. Integers are signed 64-bit
  and wrap on overflow; division truncates toward zero and `%` takes the sign of the
  dividend. An integer is a `number` while it is a safe integer and a `bigint` beyond.

### TypeScript Errors and the Stack

| Error | `error` |
|:--|:--|
| The input does not match | `SyntaxError` |
| `#recover` skipped input | `SyntaxErrors`, and `node` is set |
| A runtime error in an action | `Error` with the message of the engine |
| More nested recursive rule calls than the limit (default 100,000) | `Error`: `nesting too deep: more than 100000 nested recursive rule calls` |
| The JavaScript stack is exhausted before the limit | `Error`: `nesting too deep: the JavaScript stack overflowed at N nested recursive rule calls` |

The host stack of a JavaScript runtime is far smaller than the stack of a Go
program, so a TypeScript parser can reject nesting that the engine accepts.

### Shared TypeScript Runtime

With `-runtime import`, `parser.ts` and `types.ts` import the names they use from the module that
`-runtime-module` names. The generator does not check that module. The contract is:

- The module MUST be the `runtime.ts` that the same version of `zp` writes (`-runtime embed`, or
  `-runtime only` to refresh a copy). The parsers generated by one version need that version's runtime:
  the names, types and behavior that a parser imports are not stable between versions.
- One `runtime.ts` MAY serve any number of parsers, which are generated by that version and share its
  classes. A `Node` made by one of them is an instance of the same class as in the others.
- A generated parser carries no runtime version and the runtime has none: a runtime of another version is not
  detected when the parser is generated or loaded. It fails to type-check or to load when a name is missing
  or has another type, and may otherwise misbehave. Regenerate the parsers and the shared runtime together.
- The generator imports only the exported names of the runtime that the parser uses. The runtime's other
  exports are not part of this contract unless [Generated TypeScript API](#generated-typescript-api) lists
  them.

## Conformance

The repository tests every grammar in `examples/` and the grammars of the engine
tests against the generated Go and TypeScript parsers, in both position units and
with strings and bytes as input, and require identical trees (as JSON) and errors.
TypeScript output is type-checked with `tsc --strict` and additional strict flags.
